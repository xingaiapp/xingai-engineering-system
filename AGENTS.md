## Product Upgrade Rule

This rule applies to all XingAI products, including `meal.xingai.app`, `cook.xingai.app`, `invest.xingai.app`, `travel.xingai.app`, `outfit.xingai.app`, `routine.xingai.app`, and future `*.xingai.app` products.

> 不是重做新产品，而是在前一版上升级。

For every next version:

1. **视觉对齐 product base**: preserve the established visual language, product identity, navigation model, and primary user flow.
2. **功能继承 previous version**: inherit the previous version's core user-facing functions before adding new features.

Formula:

```txt
V2 = visual alignment with V1 + functional inheritance from V1 + V2 additions
V3 = visual alignment with V1 + functional inheritance from V2 + V3 additions
V4 = visual alignment with V1 + functional inheritance from V3 + V4 additions
```

Do not:

- Start a later version from a blank new UI.
- Replace the main product flow with an advanced dashboard.
- Remove familiar user-facing features from the previous version.
- Expose internal version labels such as V1, V2, V3, or V4 in user-facing UI.
- Make users relearn the product after each version.

Do:

- Keep the main use case as the default path.
- Add new features as optional entries, modes, pages, panels, or workflows.
- Keep advanced functionality optional until it proves it should become default.
- Use product-facing words in UI, not internal roadmap labels.

Each product should feel like the same product getting stronger — “useful new powers,” not “I have to relearn this.”

### Product examples

**Meal AI** — base: Eating Decision; decide-first flow; “What should I eat now?”; quick next-meal guidance and fiber-first eating order.

```txt
Meal V2 = Meal V1 + history/profile/trust pages
Meal V3 = Meal V2 + auth/backend/data dashboard
Meal V4 = Meal V3 + optional Health Mode / Fix My Meal
```

**Cook AI** — base stays recipe/cooking-assistance first. Later versions may add saved recipes, pantry memory, cooking modes, and nutrition or meal-prep intelligence — but must not replace the core cooking flow with an unrelated dashboard.

**Invest AI** — base stays decision-first and risk-first. Later versions may add engines, portfolio memory, MCP integrations, and richer dashboards — but must not replace the primary decision board with a generic brokerage or price-charting app.

## Invest AI Decision Boundary Rule

This rule applies to `invest.xingai.app` / `xingai-invest-ai`.

> FastAPI only reads cache. Worker/core logic computes decisions.

Before making any FastAPI logic change for Invest AI, verify the change does **not** add or move decision-engine computation into the request path.

Must follow:

1. **Worker/core owns decision logic**: macro radar, FRED factors, engine scores, consensus, risk budgets, allocations, rankings, symbol overlays, decision events, stale/degraded decision semantics, and any field that changes investment interpretation must be generated by `stock-ai-worker` or shared worker-owned core code during cache generation.
2. **FastAPI owns read/transport only**: FastAPI may read SQLite/cache rows, select a precomputed cached scope, validate/serialize payloads, enforce auth/rate limits, attach transport metadata such as `cache_meta` / `data_freshness`, and return explicit cache-miss/stale errors.
3. **No request-time decision computation**: FastAPI route handlers must not fetch live market/FRED data, recalculate macro state, blend symbol overlays, recompute consensus, change risk budgets, rank signals, or patch decision explanations on demand.
4. **Frontend renders, not decides**: React may render/localize/style explicit cached fields, but must not reverse-engineer recommendation, risk, confidence, or ranking from raw market fields.
5. **New decision field workflow**: add or change the worker-generated cache payload first, then let FastAPI expose that cached field, then let frontend render it.
